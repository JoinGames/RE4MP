# RE4MP — LAN co-op для Resident Evil 4 Remake

Прототип для Windows, REFramework и Python 3.8+. Два игрока обмениваются
позицией, поворотом и состояниями обычных дверей через локальную сеть.
Второй игрок пока отображается жёлтой проволочной фигурой. Модель персонажа,
враги, выстрелы, урон, катсцены и транспорт пока не синхронизируются.

## Следующий этап: связанный персонаж

`RE4LAN_LinkedSpawnProbe.lua` — отдельный одноразовый эксперимент для перехода
от визуальной копии к настоящему `CharacterContext`. Он вызывает подтверждённый
`CharacterManager.requestSpawn`, затем проверяет контекст, скелет, `HitController`
и Motion layers. Это ещё не включённая синхронизация: запускать только в
одноразовой тестовой сессии без сохранения и перезапускать игру после Release.
Анимации, прицеливание, выстрелы и урон будут подключаться после подтверждения
этого связанного тела.

## Версия 0.3.4: совместимость host/join и боевая диагностика

В host-отчёте v0.3.3 коллекция компонентов не поддержала вызов `get_elements`,
поэтому кнопка teleport завершилась ошибкой. v0.3.4 использует оба варианта
коллекций REFramework: `get_elements` и `IEnumerable` с перечислителем.

Замени только `RE4LAN_ModelProbe.lua` версией **0.3.4**. Основной Lua остаётся
**0.3.0**, relay — **0.2.1**.

## История v0.3.3: одежда, длительный тест и боевая диагностика

Отчёт v0.3.2 подтвердил загрузку костюма: появилось 5 готовых Mesh-компонентов,
`MeshReady=true` и `MaterialReady=true`. После удаления меши исчезли, но пустая
запись CostumeManager ещё некоторое время оставалась, поэтому очистка остановилась
безопасно на `cleanup_blocked`.

v0.3.3 увеличивает ручной тест до 180 секунд, ждёт подтверждения пустой записи
костюма перед удалением и добавляет кнопку **TEST: follow cloth (teleport)**.
Она вызывает только `GPUClothCharacter.teleportGpuCloth` у своей копии, чтобы
проверить, будет ли куртка следовать за движением партнёра. В отчёт также попадают
боевые компоненты `HitController`, контекст, HP, коллайдеры и флаги регистрации.
Это диагностика; сетевой урон ещё не включён.

Переход к урону требует тела с настоящим `CharacterContext`: текущая копия имеет
`Context=nil`, поэтому её HitController не подключён к HP владельца. Вызов
неподтверждённых `requestSpawn` или `HitManager` в обычной сессии опасен.

Замени только `RE4LAN_ModelProbe.lua` версией **0.3.3**. Основной Lua остаётся
**0.3.0**, relay — **0.2.1**. [Инструкция](docs/MODEL_PROBE.md).

## История v0.3.2: отдельная загрузка костюма

Тест v0.3.1 подтвердил, что `DrawSelf` и эффективный `Draw` включились и
оставались включёнными, но модель не появилась. У копии отсутствует
`CharacterContext`. Обход дочерних объектов завершался ошибкой даже у настоящего
Леона, поэтому прежний `mesh_count: 0` не доказывает отсутствие геометрии.

Исправлен обход `IEnumerable<Transform>`, добавлено чтение `getMesh`,
`MeshReady` и `MaterialReady`. После создания тела появилась отдельная кнопка
**TEST: apply local costume**: она запрашивает костюм локального персонажа
через `CostumeManager` только для проверенной копии. Это новый эксперимент;
его видимость и обработка `nil` callback в игре ещё не подтверждены.

Замени только `RE4LAN_ModelProbe.lua` версией **0.3.2**. Основной Lua остаётся
**0.3.0**, relay — **0.2.1**. Создай тело, нажми новую кнопку, подожди 10 секунд,
сделай скриншот и нажми Remove. Удаление теперь может ждать освобождения
костюма до 15 секунд. При `cleanup_blocked` перезапусти игру.
Пришли новый `RE4LAN_model_probe.json`. [Полная инструкция](docs/MODEL_PROBE.md).

## История v0.3.1: проверка невидимого тела

Первый тест в игре подтвердил создание отдельного объекта, его идентификаторы
и перемещение: отчёт зарегистрировал 2390 записей позы с корректным чтением
координат. Видимого персонажа пользователь не увидел. Причина невидимости пока
не установлена: v0.3.0 не собирала флаги отрисовки и состав мешей.

Model Probe v0.3.1 включает `DrawSelf` только у собственного корневого объекта,
если флаг выключен. Добавлены снимки видимости, мешей, контекста, родительских
объектов и папки, включая повторные замеры через 1 и 3 секунды. Флаги
папок, дочерних объектов и UpdateSelf не меняются.

Для этого обновления замени `RE4LAN_ModelProbe.lua`; в его меню должна быть
версия **0.3.1**. Основной `RE4LAN.lua` имеет версию **0.3.0**, relay — **0.2.1**.
После запуска теста подожди около 10 секунд и пришли новый
`RE4LAN_model_probe.json`. [Инструкция](docs/MODEL_PROBE.md).

## Версия 0.3.0: ручной эксперимент с моделью

Пользователь подтвердил, что движение в v0.2.1 стало плавнее. Скан `api4`
показал API генерации нового ID и отдельного запроса тела персонажа.
Добавлен **необязательный** `RE4LAN_ModelProbe.lua`: он запускается только
кнопкой, запрашивает одно тело текущего персонажа и пробует двигать его по
позиции партнёра. Это эксперимент, а не завершённая модель второго игрока.
На момент выпуска v0.3.0 создание и видимость ещё не были проверены в RE4;
результаты первого теста описаны выше, в разделе v0.3.1.
Анимации и бой пока не реализованы.

Основной Lua теперь находит локального игрока через `CharacterManager`, чтобы
новая копия с таким же именем объекта не подменила источник отправляемой позиции.
Визуальный эксперимент получает сглаженную позу даже при скрытой жёлтой фигуре.
Python relay остаётся версии 0.2.1, формат обмена не изменился.

**[Как запустить тест модели и получить отчёт](docs/MODEL_PROBE.md).**
Новые выводы из скана: [API4_FINDINGS.md](docs/API4_FINDINGS.md).

## Версия 0.2.1

Исправлена публикация движения: позиция теперь считывается **до** проверки,
нужно ли отправлять обновление. В исходной версии сравнивались два сохранённых
значения, поэтому движение обычно отправлялось только раз в 60 кадров.
Теперь при движении или повороте поза отправляется раз в 2 кадра
(примерно 30 Гц при 60 FPS); в покое остаётся редкий keepalive.
Ошибка записи файла вызывает повторную попытку, а не подтверждение отправки.

Relay показывает измеренную частоту чтения Lua и приёма сетевых состояний.
Сглаживание остаётся в Lua: в приложенной исходной версии relay буфера
сглаживания из старого описания нет. Формат UDP v1 сохранён.

## Установка на оба ПК

1. Нужны REFramework (`dinput8.dll` в папке игры) и Python 3.8+.
2. Закрой игру и relay. Сохрани предыдущие версии файлов для отката.
3. Скопируй `RE4LAN.lua` и `RE4MP_Scout.lua` в `<игра>\reframework\autorun\`.
   Не оставляй вторую копию того же скрипта с другим именем в `autorun`.
4. Замени `re4lan_relay.py` в папке со своими `start_*.bat`.
5. В используемом `.bat` проверь строку `set "DATA=..."`: это папка
   `<игра>\reframework\data` именно на этом компьютере. Приложенные `.bat`
   сохранены из исходного комплекта и содержат путь диска `X:`.
   На втором ПК укажи его собственный путь, например
   `C:\Program Files (x86)\Steam\steamapps\common\RESIDENT EVIL 4  BIOHAZARD RE4\reframework\data`.
6. На первом ПК запусти `start_host.bat`, на втором — `start_join.bat` и введи
   LAN IPv4 хоста. Разреши Python доступ к частной сети в брандмауэре Windows.
7. Запусти игру на обоих ПК, загрузи одинаковый участок и открой
   `Insert → RE4 LAN Co-op`. В меню должна быть версия `0.3.0` и статус `CONNECTED`.

`RE4LAN_ModelProbe.lua` устанавливается отдельно по инструкции выше.
Для обычной игры и проверки связи он не требуется.

Можно запускать relay напрямую, подставив свой путь и адрес:

```bat
py -3 re4lan_relay.py host --data "D:\Games\RE4\reframework\data"
py -3 re4lan_relay.py join 192.168.1.81 --data "D:\Games\RE4\reframework\data"
```

`start_echo.bat` / режим `echo` позволяет проверить обмен на одном ПК:
собственная фигура будет смещена на 3 метра по X. Echo не проверяет сеть между ПК.

## Проверка в игре

На обоих ПК используй обновлённые Lua и relay. Пройди по прямой 10–15 секунд,
затем повернись на месте и остановись. Во время движения при 60 FPS ожидается:

- `Lua file writes` и `Relay: Lua out` около 30 Гц;
- `network in` около 30 Гц, если партнёр тоже движется при 60 FPS;
- `Lua gap` обычно около 33–50 мс; большие значения показывают паузы публикации;
- `write fails` не растёт.

В покое примерно 1 Гц и gap около секунды нормальны. Частота зависит от FPS:
при 30 FPS целевая отправка около 15 Гц. FPS в меню приблизительный;
счётчики relay используют монотонные часы. `remote age` — время с последнего
полученного состояния, а не задержка в одну сторону.

Сними показатели **во время движения** и проверь открытие/закрытие одной двери
с обоих ПК. Если рывки остаются, нужны скриншоты меню обоих ПК и описание,
кто двигался. Режим поиска дверей `slow` остаётся известным источником пауз:
его переработка в эту итерацию не входит.

## Скан для модели второго игрока

В `Insert → RE4MP Scout` должна быть версия **v4**. Загрузи деревню, рядом
с обычной дверью и, по возможности, врагами, укажи Label `api4`, нажми `Scan now`
или F8. Результат: `<игра>\reframework\data\RE4MP_scout_api4.json`.

v4 выгружает необходимые enum и структуры до общего лимита, сохраняет доступные
живые контексты игрока и первых трёх врагов и отмечает недоступные типы/поля.
Это чтение данных; скрипт не создаёт персонажей и не меняет игровой мир.
Скан `api4` уже получен и проанализирован. Повторять его сейчас не нужно:
следующий отчёт — `RE4LAN_model_probe.json` из теста модели.

## Разработка и проверки вне игры

Relay работает без сторонних пакетов. Для тестов установлен Lua 5.4 через Lupa:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m unittest discover -s tests -v
```

В PowerShell используй `.venv\Scripts\python.exe` вместо `.venv/bin/python`.
В текущей облачной среде готовый интерпретатор:
`/workspace/re4mp-dev-venv/bin/python`.

Тесты исполняют Lua-файлы с подставным API REFramework и запускают настоящие
процессы relay `host`/`join`/`echo` на loopback. Они проверяют частоту публикации,
поворот, исчезновение игрока, восстановление после ошибки записи, приоритет
типов разведчика, передачу состояний и метрики. Нативный API REFramework,
файловые блокировки Windows и поведение внутри RE4 проверяются отдельно в игре.

См. [состояние разработки](docs/DEVELOPMENT.md) и
[исходную передачу проекта](docs/RE4_LAN_COOP_HANDOFF.txt).
