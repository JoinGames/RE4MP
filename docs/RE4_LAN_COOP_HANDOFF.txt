ПРОЧТИ СНАЧАЛА (как пользоваться этим файлом)
---------------------------------------------
1. Пользователь пишет по-русски. Отвечай по-русски, дружелюбно, без воды.
2. В новом чате пользователь должен ПРИКРЕПИТЬ файлы из списка в разделе 9
   (иначе у тебя не будет кода). Если какого-то файла нет — скажи об этом и попроси.
3. Ты НЕ можешь запускать игру. Всё тестирует пользователь на ДВУХ своих компьютерах.
   Поэтому: каждое изменение делай небольшим, проверяй структуру кода и логику
   симуляцией (см. раздел 10), честно говори, что в игре не проверено.
4. Не пиши мод "вслепую" на классах, которых нет в данных скана. Сначала смотри
   факты в разделе 5-6 и в приложенных JSON-сканах. Угаданные имена методов -
   это риск; помечай их как эксперимент и делай переключаемыми в меню.
5. Первым делом в новом чате: прочитай раздел 8 (что делать дальше) и спроси
   пользователя результаты последних тестов (раздел 7).

1. ЦЕЛЬ ПРОЕКТА
-------------------------------------------------------------------------------------
Пользователь хочет:
 (A) Мод NOCLIP + FREECAM для RE4 Remake (ГОТОВ, работает - см. раздел 2).
 (B) СВОЙ локальный (LAN) кооператив для RE4 Remake, потому что готовый мод claybtv
     ("RE4 Multiplayer", Nexus) кривой: не синхронизированы двери, лодки, анимации в
     катсценах, частые вылеты. Нужен только LAN, без интернета/аккаунтов/серверов.
     Желаемое: видеть друг друга (с моделью персонажа), синхронные двери, враги,
     катсцены, лодка. Это делается ПОЭТАПНО (раздел 3).

Платформа: Resident Evil 4 Remake (Steam, PC, Windows), REFramework (dinput8.dll),
Lua-скрипты в <игра>\reframework\autorun\. В Lua REFramework НЕТ сокетов -> сеть
сделана внешней Python-программой (relay), общение через JSON-файлы.

2. ЧАСТЬ A: RE4R_NoclipFly.lua (ГОТОВО, пользователь подтвердил "всё работает")
-------------------------------------------------------------------------------------
Файл: RE4R_NoclipFly.lua (~1158 строк). Клавиша по умолчанию G включает/выключает.
Что делает: полёт по WASD (+ вверх/вниз), камера вращается мышью, Леон бессмертен и
невидим, при выходе возвращается; FOV, скорость и т.д. настраиваются в меню REFramework.

История проблемы и решение (важно помнить, чтобы не повторять ошибок):
 * Первая версия двигала игрока вместе с камерой. Игра считала, что Леон ПАДАЕТ, и
   наклоняла камеру вниз. Заморозка логики GameObject (UpdateSelf=false) убирала
   наклон, но ломала вращение камеры мышью.
 * Вывод: вращение камеры мышью и "взгляд вниз при падении" живут в одном компоненте
   на Леоне, разделить заморозкой нельзя. Покомпонентная заморозка ("smart"/"physics")
   тоже НЕ помогла.
 * РЕШЕНИЕ (работает): режим "detached" (по умолчанию, cfg.mode="detached"):
   Леон остаётся стоять на земле (каждый кадр его warp-ят на место), летит только
   КАМЕРА: скрипт переписывает ПОЗИЦИЮ камеры (rotation оставляет игре - её крутит
   мышь сама игра). Позиция камеры пишется в нескольких точках кадра:
   re.on_application_entry "UpdateBehavior", "LateUpdateBehavior", "PrepareRendering"
   и re.on_pre_application_entry "BeginRendering". При выходе Леон телепортируется
   туда, где остановилась камера (на cfg.exit_drop метров ниже камеры), + 10 c
   бессмертия.
 * Старый режим "follow" (игрок летит вместе с камерой) оставлен как опция, но камера
   там может наклоняться вниз.
 * Ограничение detached-режима: мир не подгружается вокруг камеры (подгрузка идёт от
   Леона), пока летишь далеко.
 * Имя объекта игрока: "ch0a0z0_body" (PLAYER_OBJECT).
 * Конфиг пишется через json.dump_file в reframework/data.

4. АРХИТЕКТУРА LAN-МОДА (то, что реально сделано)
-------------------------------------------------------------------------------------
4.1 Компоненты
  RE4LAN.lua        - Lua-мод (v0.2), кладётся в <игра>\reframework\autorun\ у ОБОИХ.
  re4lan_relay.py   - Python 3 (только stdlib). Режимы: host / join <IP> / echo (тест
                      в одиночку: relay "отвечает" твоим же состоянием, сдвинутым на +3 м по X).
                      Аргументы: --data "<игра>\reframework\data" --port 7777 (по умолч.)
  start_*.bat       - запуск двойным кликом (пути пользователя вшиты, см. раздел 9).

4.2 Файлы обмена (в <игра>\reframework\data\), префикс RE4LAN_ (НЕ RE4MP_ - тот
    префикс использует чужой мод):
  RE4LAN_out.json    Lua -> relay:  { seq, name, pos=[x,y,z], yaw, doors={key={s,v,d}}, ev=[{id,k,s,v,d}] }
  RE4LAN_in.json     relay -> Lua:  { seq, d={ ...то же самое от партнёра... } }
  RE4LAN_status.json relay -> Lua:  { t, role(host|join), mode, connected, peer, ping_ms,
                                      tx, rx, wfail, out_hz, in_hz, out_gap_ms, delay_ms, gap_ms }
  RE4LAN_cfg.json    настройки Lua-мода (имя, галочки, open_method и т.д.)
  Запись из Lua: json.dump_file (НЕ атомарна); relay при чтении ловит недописанный файл и
  повторяет. Запись relay -> Lua: через временный файл + os.replace (атомарно).
  Пустые Lua-таблицы json.dump_file пишет как null - учитывать при чтении в Python.

4.3 Сетевой протокол relay <-> relay (UDP, порт 7777, брандмауэр Windows нужно разрешить)
  Пакет = байты "RE4L" + JSON (ASCII). Типы:
   {"k":"hi","v":1}                    приветствие (host узнаёт адрес клиента)
   {"k":"p","t":время} / {"k":"o","t"} пинг / понг
   {"k":"s","ts":время_отправителя,"d":<содержимое out.json>}   состояние
  Связь считается установленной, если пакеты приходили < 3 c назад.

4.4 Сглаживание позиции (jitter buffer) В RELAY (класс Smoother) - добавлено в конце этого
  чата, протестировано только на Linux:
   - принимающий relay хранит снимки (pos,yaw) с временем отправителя ts, приводит к своим
     часам через минимум смещения (off), рисует с задержкой delay = clamp(1.5*gap_ema+0.03, 0.05, 0.9),
     интерполирует, при нехватке данных экстраполирует до 0.2 c;
   - пишет RE4LAN_in.json с сглаженной позицией до ~60 раз/с (только при изменениях);
   - в статус добавлены метрики out_hz (как часто Lua публикует), in_hz, out_gap_ms
     (макс. пауза между публикациями Lua за секунду), delay_ms, gap_ms.
  ТЕСТ (имитация отправителя с паузами по 0.5 c и пачками): без сглаживания скачок позиции
  мог быть до 275 см, после - макс. ~29 см; но delay вырос до ~459 мс (из-за плохого входа).
  ВАЖНО: Lua-часть (RE4LAN.lua) ЕЩЁ НЕ ОБНОВЛЕНА под это: она всё ещё сама сглаживает
  (lerp 0.35 + экстраполяция по скорости) и показывает ложные "data rate" на основе
  os.clock (это CPU-время, а не реальное). Нужно: убрать двойное сглаживание, показывать
  метрики из status.json (out_hz/in_hz/out_gap_ms/delay_ms/gap_ms) и FPS по os.time().

4.5 Синхронизация дверей (RE4LAN.lua, функции door_pass / receive_events / merge_world)
  - Класс: chainsaw.GmDoor. Ключ двери: "имя|x|y|z" (координаты округлены до 0.1;
    имена не уникальны, позиции статичны и одинаковы на обеих машинах).
  - Состояние "открыта": get_IsOpen()==true ИЛИ поле _Routine ~= 0 (в покое у ВСЕХ дверей
    _Routine=0, _OpenValue=0 - проверено по сканам).
  - Событийная модель: при локальном изменении -> версия v+1, событие {id,k,s,v,d}
    (id = os.time()*1000 + счётчик, растёт между перезапусками). События рассылаются
    повторно ~300 кадров (защита от потерь UDP), приёмник дедуплицирует по id.
    Приёмник воспроизводит события ПО ПОРЯДКУ, между двумя событиями одной двери
    минимум 18 кадров (чтобы быстрый "открылась-закрылась" был виден).
  - Параллельно рассылается снимок мира doors={key={s,v,d}} - страховка для дверей,
    загруженных позже (стриминг).
  - Антипинг-понг: после применения чужого события 90 кадров "самопроизвольные"
    изменения не считаются своими. При равенстве версий побеждает ХОСТ.
  - Отложка: если дверь только начала открываться (_CurRot ~ 0), ждём до 12 кадров, чтобы
    узнать сторону (знак _CurRot).
  - Применение у приёмника (cfg.open_method): 1 = makeOpened()/makeClosed() (мгновенно,
    РАБОТАЕТ); 2 = setKickOpen() (экспериментально, пользователь ещё не проверил).
    cfg.copy_dir (экспериментально): перед makeOpened ставит IsKickOpenSideA, после -
    пишет _CurRot = dir*RotOpen. Результат пользователем пока не подтверждён.
  - ВАЖНЫЙ БАГ (причина "дверь не открывается при быстром пробеге" и подвисаний):
    быстрый поиск дверей (scene:call("findComponents(System.Type)", typeof("chainsaw.GmDoor")))
    у пользователя НЕ сработал -> мод ушёл на медленный обход всей сцены, который в коде
    выполняется раз в ~240 кадров (4 c) и занимает ~48 мс; между обходами find_doors()
    возвращает nil и door_pass ничего не делает => задержка двери до 4 с + подвисание.
    В меню видно: "Doors: 26 found (slow search, pass 48.00 ms)".

4.6 Отрисовка второго игрока: проволочная фигура через draw.world_to_screen / draw.line /
    draw.filled_circle / draw.text (голова, шея, плечи, руки, таз, ноги, линия взгляда),
    имя и расстояние над головой. yaw считается из кватерниона:
    yaw = atan2(2(wy+xz), 1-2(y^2+z^2)); "вперёд" = (sin yaw, 0, cos yaw) (предположение +Z).

6. ПРАВИЛА/ГРАБЛИ REFramework Lua, на которые мы уже наступили
-------------------------------------------------------------------------------------
 * td:get_methods() / td:get_fields() возвращают НЕ Lua-таблицу (userdata) -> проверка
   type()=="table" отбрасывает результат. Нужен обход через ipairs/pairs/числовой индекс в pcall
   (функция to_list в разведчике).
 * "a and b or c" с b==false даёт c. Для булевых состояний писать явным if.
 * os.clock() - ПРОЦЕССОРНОЕ время (в многопоточной игре идёт не как реальное). Для реального
   времени: os.time() (секунды) или счётчик кадров; из Python-стороны берём точное время.
 * json.dump_file пустую таблицу пишет как null.
 * Вызовы методов на уже выгруженных (уничтоженных) объектах могут уронить игру: не хранить
   указатели на компоненты между кадрами дольше необходимого, всё оборачивать в pcall,
   список объектов брать свежим перед использованием.
 * Перегруженные методы вызывать с сигнатурой: c:call("findGameObject(System.String)", name),
   getPlayerContextRef() - вероятно нужна сигнатура "getPlayerContextRef()".
 * Поля, в т.ч. backing-field: comp:get_field("<KindID>k__BackingField") читается.
 * Для получения System.Type использовать td:get_runtime_type() (основной вариант, ещё НЕ проверен у
   пользователя) или sdk.typeof(name). Мой код использовал sdk.typeof -> fast-поиск не сработал.
 * Названия точек кадра для re.on_application_entry: "UpdateBehavior", "LateUpdateBehavior",
   "PrepareRendering", "BeginRendering" (pre). Работают.
 * draw.text / draw.line / draw.filled_circle / draw.world_to_screen работают (видно на скриншотах).
 * Пустые строки/метки: скан-файл называется RE4MP_scout_<метка>.json в reframework/data.
 * В outputs-скане: ограничение "ncollected >= 160" в разведчике v3 обрезало типы по алфавиту
   (дошли только до chainsaw.Ch1f2z0...) - из-за этого НЕТ DoorSide, ContextID, CharacterKindID.
